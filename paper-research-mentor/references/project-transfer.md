# Project-aware methodological advice

Inspect supplied context and relevant authorized README/configuration/data/metrics as needed; register the documents actually supporting project facts. Do not scan unrelated folders or treat stale memory as live truth.

Profile: target/output, data/evaluation unit, constraints, baseline, success metric and resources. Store `project` records with evidence-linked facts; absent facts remain unknown. With no context use an unknown-only project record (`facts: {}`, `context_status: unavailable`, unknowns listed, empty evidence IDs). Do not attach unrelated paper evidence to invented project facts. No context means conditional directions, not a diagnosis.

Compare keeping the baseline, low-cost borrowing and larger exploration. State what would change the recommendation. Each `transfer` record contains problem, mechanism, assumptions, baseline difference, minimal experiment, metrics/cost, stop criteria, strategy and evidence IDs; classify it as `proposal`.

Specify controls, success/failure interpretation and what not to conclude. Check domain alignment, signals, training/inference constraints, leakage, fair tuning, compute/capacity confounds and simpler alternatives. Estimates remain estimates. A plausible mechanism is not an observed project improvement.

When interaction is welcome, invite the user's hypothesis before favoring a combination. Reflect it accurately, examine support and grounded objections, and propose a discriminating test. Do not invent consensus or objections merely for balance.

Use decision cards: “If A holds, test B; if C occurs, prefer D; abandon at E.” Keep the user's commitments separate from recommendations. Reading authorization does not authorize code changes, training, deployment or publication.
